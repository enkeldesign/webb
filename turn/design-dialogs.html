Normative component pattern

TURN DIALOGS

One interaction model and one visual anatomy, with deliberate size variants for short decisions, settings, rich tools and long-form reading.

Principles Inventory Anatomy Sizes Behaviour Specimen
01 · Decision

Standardize the shell, not the content.

TURN dialogs should feel related and behave predictably. A Trophy Road tool, a denial alert and a long history reader do not need the same dimensions or internal layout.

Structure

Native dialog

Use <dialog>, an accessible name, one visible heading and a real close control.

Ownership

One scroll surface

The shell remains stable. Long content scrolls inside the body rather than moving the close control away.

Variation

Named sizes

Choose compact, standard, wide or reader. Avoid one-off pixel widths tied to a single feature.

03 · Anatomy

A stable frame around changing content.

Class names describe responsibility. Feature classes may extend the body but should not redefine the complete shell.

  1. .turn-dialogThe native dialog element. Owns viewport bounds, backdrop and size variant.
  2. .turn-dialog__surfaceThe bordered TURN card. Owns padding, radius, hard shadow and overflow boundary.
  3. .turn-dialog__headerEyebrow, h2 and close button. Remains visible in reader dialogs.
  4. .turn-dialog__bodyThe sole scroll owner when content exceeds the available block size.
  5. .turn-dialog__actionsOptional grouped actions. Use buttons for commands and links for navigation.
04 · Size scale

Four named choices.

Choose the smallest size that supports the content without cramped controls, excessive wrapping or unnecessary empty space.

Compact

≈ 660 px

About, alerts and short explanations.

Standard

≈ 760 px

Feedback, simple settings and focused tasks.

Wide

≈ 1040 px

Card grids, complex settings, training and progression.

Reader

Near full screen

Long documents, tabs and dense lists where stable navigation matters.

05 · Behaviour

Predictable focus and dismissal.

Visual consistency without consistent keyboard, screen-reader and scroll behaviour is not a component system.

Opening

  • Record the invoking control.
  • Reset the intended scroll surface to the top.
  • Focus the close control unless feature testing proves another target is better.
  • Use preventScroll when available.

Closing

  • Close button and backdrop dismiss ordinary dialogs.
  • Escape uses native dialog behaviour.
  • Return focus to the invoking control.
  • Do not return focus to an element inside a dialog that is now closed.

Long content

  • Keep header and tab controls outside the scrolling body.
  • Use one internal scroll owner.
  • Contain overscroll to avoid moving the game beneath the dialog.
  • Do not shrink body text below a comfortable reading size merely to fit more.

Dialog transitions

  • Do not stack modal dialogs.
  • Close the source, open the destination, then restore the source when appropriate.
  • Tabs belong inside one dialog when they describe parallel views of the same object.
  • Use a separate dialog when the task changes substantially.
